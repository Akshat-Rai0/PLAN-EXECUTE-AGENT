How it should work

For every goal in src/eval/golden_dataset.py, this page traces the ideal run through the plan-and-execute graph: every node that activates, in order, the state each node returns, and where the human-in-the-loop gate pauses. The planner is an LLM — real plans vary run to run — so these are canonical flows consistent with each goal's expected_step_count, required_capability and category mechanics.

01 · Lifecycle in one paragraph

The shape of every run

Every goal enters at START → plan. The plan node calls breakdown_task() — one LLM call that returns a JSON plan of steps (id, task, tool_hint, status=PENDING). Two deterministic shortcuts can fire here: a pure date query skips planning entirely, and any goal containing recency language (latest, current, now, this year, most recent…) gets a date-anchor step prepended — a step that is born DONE with today's real date, so no search ever guesses the year.

The executor then marks exactly one PENDING step RUNNING per visit, and a conditional edge routes it by tool_hint: LOW-risk hints go straight to their tool node; anything HIGH-risk (or unrecognized) is intercepted by the approval node, which pre-generates the exact operation (command / path / file / synthesis preview) and calls LangGraph's interrupt() — the graph physically pauses until a human approves.

After every tool node, control funnels through check_new_info: if the step FAILED → replaner (failure recovery). If the step succeeded but surfaced novel information (LLM novelty check against everything learned so far) → replaner again, this time to refine the remaining steps with what was just learned — that is the whole point of the new_information category. Otherwise → back to the executor for the next step.

When no PENDING step remains, the router sends the run to synthesize, which concatenates every step result/error and streams the final answer into plan.final_answer → END.

Reading the per-case diagrams. Each diagram shows all 21 registered nodes; only the nodes a given ideal run touches are lit. Numbered badges give activation order (a badge stack like 2·6·9 means the node fired three times). Solid blue arrows are the path actually taken; everything else stays faint. Amber-bordered nodes are HITL pause points.

Honesty note: three nodes are registered in build_graph() but unreachable via routing — stub (kept for backward compat), ask_human and extract_user_info (wired outgoing-only; nothing routes into them). They appear greyed/dashed everywhere.

_route_after_check — the post-tool fork

The first-executed info step never triggers a success-replan. _detect_new_information() compares a step result against cumulative_context — and the very first completed info step compares against an empty list, which is defined as "not novel". Also note the date-anchor step never enters cumulative_context at all (it is born DONE inside plan_node and never routed through check_new_info). So success-based replanning starts earliest at the second executed search/browser/code step.

Silent skip list: shell / write_file / delete_file / start_server / setup_workspace results never even get a novelty LLM call — they don't gather external knowledge — but their entries still land in cumulative_context.

_route_after_tool — the two hard exits

Normally every tool node flows to check_new_info. Two conditions short-circuit straight to synthesize: steps_executed ≥ MAX_TOTAL_STEPS (15) (remaining PENDING/RUNNING steps get CANCELLED with an explanatory error), or any step already CANCELLED. This is how runaway runs still terminate with an honest partial answer.

_route_after_approval — after the human decides

  • approve → the exact tool node matching the hint runs for real (pre-generated command/path/file cached on the step as _PENDING_COMMAND / _PENDING_PATH / _PENDING_FILE_PATH / _PENDING_SCHEMA is reused verbatim — the human approves what will actually execute).
  • reject → step marked FAILED ("Operation rejected by human"); with no RUNNING step left the router falls back to executor.
  • alternative → the replacement instruction is stored as ALTERNATIVE_INPUT: … on the step and folded into the tool task (browser_use consumes it explicitly).
